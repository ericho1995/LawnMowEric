# Independent review of v0.1.0

Two independent review agents were run against the v0.1.0 tag, in parallel,
with no visibility into each other's findings: one reviewing `index.html`
for code/security correctness, the other reviewing `docs/requirements.md`
against `index.html` for content, business-logic, and legal/compliance
gaps. Their raw findings are recorded below for traceability. Everything
marked resolved was fixed in v0.2.0 (see `CHANGELOG.md`); anything not
resolved is carried into the requirements doc as an open question or
documented limitation instead.

## Review 1 — code/security (index.html)

- **[Resolved]** HIGH — `d.status` and `doc.id` interpolated into HTML
  attributes without escaping (stored-XSS risk given the `db` capability
  allows any signed-in viewer to write directly to the collection).
- **[Documented, partially mitigated]** HIGH — `?admin` was pure
  client-side convenience with no real access control, exposing customer
  PII/access notes to anyone past it. Added a passphrase gate as a
  stopgap and documented plainly (in-page and in the requirements doc)
  that it is not real authentication.
- LOW — no server-side validation on writes (anyone with console access
  could write arbitrary status values). Mitigated client-side by clamping
  rendered status to the known enum; real validation needs a real backend
  (Phase 2).
- **[Resolved]** MEDIUM — duplicate "Open email draft" links accumulated
  on repeated failed submits.
- Open (accepted for Phase 1) — admin list is fully torn down and
  rebuilt on every snapshot, which can lose in-progress interaction
  (e.g. an open dropdown). Acceptable at Phase 1 volume; worth revisiting
  if the admin view sees heavier concurrent use.
- **[Resolved]** MEDIUM — status-update failures were silently swallowed;
  now rolls back the UI and shows an inline error.
- LOW — minor race between capability init and user interaction (accepted
  as-is; the email fallback path handles it gracefully).
- **[Resolved]** MEDIUM — dynamic status/success messages weren't
  announced to screen readers; added `aria-live`/`role="status"`.
- **[Resolved]** LOW — admin status `<select>` wasn't associated with its
  `<label>`; added `for`/`id`.
- **[Resolved]** LOW — borderline color contrast on the "Contacted" status
  color; darkened to meet WCAG AA.
- Confirmed clean: no duplicate ids, balanced tags, no unclosed elements.

## Review 2 — content/business-logic (requirements.md vs. index.html)

- **[Resolved]** "Insured & vetted"/identity-checked claims were unverified
  and a genuine Australian Consumer Law risk (misleading conduct) for a
  solo-operator business with insurance status still an open question.
  Rewritten to state what's true today and frame vetting as a future
  commitment.
- **[Resolved]** Hero copy implied an existing pool of mowers; corrected to
  reflect that Eric does every job personally today.
- **[Flagged to owner]** The "come back and make it right" satisfaction
  guarantee was never explicitly signed off by Eric — softened slightly,
  and added as an explicit open question (§14.8) rather than assumed.
- **[Documented]** No privacy notice at the point of collection, despite
  the form collecting personal information now. Added a stopgap data-use
  line on-site and reclassified this as a Phase 1 (not Phase 2+) issue in
  the requirements doc.
- **[Documented, partially mitigated]** `?admin` had no authentication
  despite being labelled "Business login." Relabelled honestly, added a
  passphrase gate (see Review 1), and documented the real fix (proper
  accounts) as Phase 2 work.
- **[Carried to open questions]** ABN/business name registration and GST
  status — genuine decisions for Eric, not something this review can
  resolve; added to §14.
- **[Resolved]** `hello@mowmate.com.au` fallback address doesn't exist yet
  (no real domain in Phase 1); switched to Eric's real monitored address.
- **[Resolved]** Sydney sub-regions were listed as "coming soon" with more
  certainty than the doc's own open-question status supported; genericized
  to "timeline not yet set."
- **[Resolved]** "Simple, flat pricing" asserted a pricing model that's
  still an open decision (§14.2); softened to a claim that's true
  regardless of which model is chosen.
- **[Added]** Requirements doc gaps: testing/QA approach, budget &
  timeline, competitive positioning (Airtasker/Hipages), data
  retention/export plan, and how Eric gets paid before Phase 2 payments
  exist — all added as new sections (§§10–13).
